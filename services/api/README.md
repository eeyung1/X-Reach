# X-Reach API

The FastAPI service extracts local multimodal draft features, validates the
resulting action propensities, and delegates scoring and optional reach
calibration to the Rust `xreach-core` crate through the JSON-lines scorer in
`rust-bridge/`. Callers can submit text and media directly without constructing
prediction JSON. Percentile output is `null` until historical score calibration
data is configured.

## Setup

```bash
python -m pip install -e "../multimodal[inference]" -e "../radar" -e ".[test]"
cargo build --release --manifest-path rust-bridge/Cargo.toml
uvicorn xreach_api.main:app --app-dir src --reload
```

The Rust bridge uses the workspace `crates/xreach-core` via a relative Cargo
path dependency. Set `XREACH_SCORER_BIN` to use a prebuilt scorer executable.
If unset, the API lazily builds the bridge when the first score is requested.

## Live radar stream

`GET /api/v1/radar/stream` is a server-sent event stream of fresh viral root
posts found by the radar scout. Configure `XREACH_RADAR_CAPTURE_FILE` to point
to a JSON HAR or REA capture snapshot that an external capture process refreshes;
the API background producer scans changed snapshots every five seconds by
default. Set `XREACH_RADAR_POLL_SECONDS` to change that interval. With no capture
file configured, the endpoint stays open and sends heartbeat events while
waiting for seeds.

Events include a monotonically increasing `id`, `event: seed`, and JSON seed
data. Pass `Last-Event-ID` to replay newer entries from the in-memory ring, or
filter by cluster with `?simcluster=Technology` (repeat the parameter for more
labels). If a reconnect asks for history older than the ring, the stream sends
an `event: reset` notice before the available events. The buffer holds the most
recent 500 seeds per API process; run a single API worker when clients need one
continuous event history.

## Analyze a draft

`POST /api/v1/analyze` accepts JSON text or `multipart/form-data` with a `text`
field and up to four `media` files. It invokes the local multimodal package and
returns Local Topic Codes, keyframe timing, inferred action propensities and the Rust
score. Existing callers may continue supplying `predictions` in JSON or as a
JSON-encoded multipart field to bypass automatic extraction.

```json
{
  "text": "A short draft",
  "text": "A short draft"
}
```

The response includes weighted and final model scores, visibility drops, the
six-level `local_topic_codes`, compact multimodal metadata (never raw embeddings),
and an explicit `score_calibration_status` of `unavailable` with a null
`model_score_percentile` by default. These codes are generated by this project's
local quantizer; they are not official X Phoenix Semantic IDs. OpenCLIP loads
lazily on the first automatic request; missing inference dependencies produce a
503 without preventing the API from starting or manual-prediction requests from
working.

## Radar daemon ingestion

The standalone `xreach-radar daemon` process publishes seed batches to
`POST /api/v1/radar/events`; the API stores them in the same bounded ring used by
`GET /api/v1/radar/stream`. Set the same `XREACH_RADAR_INGEST_TOKEN` in both
containers to require a bearer token. If the token is omitted, ingestion is
unauthenticated and should only be exposed on a private container network.

## Radar alerts

Set `XREACH_ALERT_ADMIN_TOKEN` to enable alert administration. Supply it in the
`X-Alert-Admin-Token` header when calling `GET` or `PUT /api/v1/alerts` and
`POST /api/v1/alerts/test`. The configuration replaces the current process's
rules and webhook targets; webhook secrets and URL paths are never returned by
the configuration response. A test request evaluates a sample seed against a
selected rule and attempts delivery to every configured target. Matching seeds
received by `/api/v1/radar/events` are dispatched in a FastAPI background task.

```json
{
  "rules": [
    {
      "rule_id": "fast-tech",
      "min_views_per_minute": 500,
      "max_age_minutes": 30,
      "simclusters": ["Technology"]
    }
  ],
  "webhooks": [
    {
      "webhook_id": "team-chat",
      "url": "https://hooks.example.test/endpoint",
      "secret": "replace-with-a-random-secret",
      "format": "slack"
    }
  ]
}
```

Alert settings are held in process memory and must be configured again after a
restart. Keep one API worker while relying on radar ingestion and alert delivery,
as each process has its own settings and event buffer.

## Versioned telemetry contracts

`xreach_api.models` defines strict Pydantic v2 records for draft inputs,
account context, publication context, and observed outcomes. Each record uses
`schema_version: "v1"`, timezone-aware timestamps, and rejects unknown fields.
Draft records require text or media metadata. Publication records link a draft
to a published post and validate that direct root replies target their
conversation root. Outcome records represent one observation horizon per
record; supported horizons are `5m`, `30m`, `2h`, `24h`, and `7d`.

The closed-loop API accepts draft registration at `POST /api/v1/telemetry/drafts`
with a `creator_id` and optional `baseline_24h_impressions`, publication links
at `POST /api/v1/telemetry/publications`, and observed snapshots at
`POST /api/v1/telemetry/outcomes`. The bridge accepts 24h and 7d outcomes and
requires every outcome's `draft_id` and `published_tweet_id` to match its
registered publication. `GET /api/v1/telemetry/summary` reports attributed
posts, horizon coverage, and mean Creator Lift Delta. Lift is the mean percent
difference between observed 24h impressions and the supplied creator baseline;
posts without a positive baseline are excluded. This initial store is
process-local, so it resets on restart and should run as a single API worker.

```json
{
  "schema_version": "v1",
  "draft_id": "97bb1fd8-3e1d-4d46-9c06-812f57f231d5",
  "published_tweet_id": "1234567890",
  "horizon": "24h",
  "observed_at": "2026-11-04T12:00:00Z",
  "source": "platform_api",
  "impressions": 12000,
  "likes": 240,
  "replies": 35
}
```

## Model score calibration and uncertainty

Set `XREACH_SCORE_CALIBRATION_FILE` to a JSON calibration file to enable model
score percentiles. The legacy `XREACH_REACH_CALIBRATION_FILE` name remains
accepted for existing deployments. The empirical method uses historical final
model scores as a reference distribution; equal scores receive their average
rank and values outside the sample map to 0 or 100. For example:

```json
{"method":"empirical","reference_scores":[0.001,0.04,0.12,0.8]}
```

The parametric method fits a log-normal distribution to positive historical
model scores. Supply the mean and population standard deviation of their
natural logarithms:

```json
{"method":"log_normal","log_mean":-1.2,"log_std_dev":0.8}
```

Both methods return rank within the configured historical score distribution;
this is not reach probability or a forecast of impressions. Empirical
calibrations also return `model_score_percentile_bounds`, a 95% distribution-free
confidence band computed with the Dvoretzky-Kiefer-Wolfowitz inequality. A
log-normal configuration contains neither fit sample size nor parameter
covariance, so its bounds are null rather than fabricated. Populate reference
data from a representative set of observed posts; the service does not ship
with a calibration dataset. `/api/v1/analyze` and `/api/v1/placement` always
include `model_limitations`, and placement includes the score percentile and
bounds for the recommended surface and each candidate score.

## Compare placement

`POST /api/v1/placement` accepts `profile_predictions` and
`direct_root_reply_predictions`. Both alternatives are scored independently by
the Rust core. The higher surviving score is recommended; ties favor a profile
post. Model score percentile remains unavailable without calibration.
